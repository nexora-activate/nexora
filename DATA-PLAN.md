# Data Plan

## Serveur autonome Node/Bun + Postgres (Supabase) + SMTP — détachement de la plateforme d'hébergement (2026-11-19)
- Demande de sniko (verbatim, résumé fidèle) : « adapte la plateforme NEXORA pour en faire un vrai serveur autonome, prêt à déployer sur Render (plan gratuit) » et « tu l'actives sur NEXORA » — approuvé par sniko. La plateforme ne dépend plus d'aucun SDK ni service de l'ancien hébergeur : un seul processus Bun sert le client et les actions, la base est un vrai Postgres, les e-mails partent en SMTP.
- **Point d'entrée `server/src/index.ts`** : serveur HTTP (`node:http`) qui écoute sur `process.env.PORT` (défaut 3000), sert `client/dist` en statique (repli SPA sur index.html — le retour OAuth Discord arrive sur l'adresse du site avec `?code&state`), `GET /healthz`, et la RPC **POST /actions** (corps JSON `{action, args}` → `{data}` en succès, `{error, issues?}` sinon — même format que l'ancien client consommait). Au démarrage, il applique les migrations Drizzle à la base `DATABASE_URL` (idempotent : une base Supabase neuve reçoit ses tables sans étape manuelle ; en cas d'échec, le serveur reste debout et la page s'affiche, l'erreur est dans les journaux). `package.json` : `"start": "bun run server/src/index.ts"`, `"build"` construit le client (`client/build.mjs`, Bun.build + bun-plugin-tailwind, sans SDK) ET le serveur (`bun build server/src/index.ts` → `server/dist/index.js`). Vérifié en local : typecheck client + serveur sans erreur, build OK, `bun run start` sert l'accueil (200, titre NEXORA), et tests de bout en bout contre un vrai Postgres (PGlite) — migrations au démarrage, inscription/connexion/session, Patron par e-mail, offres/badges, API bot, support — tous verts (26 vérifications actions + 8 vérifications HTTP).
- **Base Postgres (Supabase)** : `server/src/schema.ts` réécrit en `drizzle-orm/pg-core` (pgTable, `serial`, `timestamp mode: "date"` — mêmes tables/colonnes : users, verification_codes, sessions, server_requests, bot_subscriptions, email_deliveries, support_messages, notification_emails, discord_config, discord_login_codes) ; accès via `server/src/db.ts` (pool `pg`, `drizzle-orm/node-postgres`, paresseux : aucun échec tant qu'aucune requête n'est faite). Les 7 migrations `drizzle/0001…0007` sont réécrites en dialecte Postgres (serial, timestamp, aucun backtick ; la 0001 crée toujours la table jetable `entries`, supprimée en 0002) et le journal passe en dialecte `postgresql`. `drizzle.config.ts` ajouté (`bun run db:migrate` possible) ; dépendances ajoutées : `pg`, `drizzle-kit` (+ `@types/pg`). `adminGetDatabaseStatus` marche comme avant (SELECT 1 sur DATABASE_URL, via le pool de l'application — aucune connexion en plus, ce qui compte sur le quota Supabase gratuit ; l'URL n'est jamais renvoyée ni journalisée). **DATABASE_URL est la vraie base de l'application** — il n'y a plus de base locale de repli (les textes admin « base locale » des 5 langues disent maintenant que la base n'est pas configurée tant que DATABASE_URL est absente).
- **E-mails SMTP (Nodemailer)** : `server/src/mailer.ts` envoie via smtp.gmail.com:465 (TLS) depuis **nexora.activate@gmail.com**, mot de passe d'application lu dans **`GMAIL_APP_PASSWORD`** (jamais en dur ; absent → échec propre). Fini les tâches d'agent : `requestSignupCode` envoie le code HTML directement puis marque la ligne `email_deliveries` **envoye/echec selon le résultat SMTP** ; `notifyNexora` (support + demandes de serveur vers nexora.activate@gmail.com) fait pareil dans `notification_emails`. Les actions `markCodeEmailDelivered` / `markNotificationEmailDelivered` existent toujours et mettent à jour le même suivi. Sans mot de passe d'application, l'inscription répond « L'envoi de l'e-mail a échoué » et le statut de livraison affiche `echec` — comportement vérifié dans les tests.
- **Cadre maison `server/src/framework.ts`** (remplace l'ancien SDK pour les actions) : `defineAction`/`z`/`Ctx`/`ActionsModule` aux mêmes formes — les handlers d'`actions.ts` sont inchangés sauf les deux envois d'e-mails. `ctx.db()` = le Drizzle Postgres ; `ctx.executePrivileged` appelle en processus les services de `server/src/privileged.ts` (crypto scrypt/SHA-256, échange OAuth Discord, lecture d'environnement à liste blanche, sonde base — mêmes implémentations, la sonde utilise maintenant le client `pg`), dispatchés par nom de contrat depuis `server/src/ctx.ts`. Côté client : `client/src/api.ts` = un simple `fetch` POST vers `./actions` (même enveloppe `{action, args}` → `{data}`, erreurs en `ActionError` avec `status`/`issues`) ; `actionFields` est recréé en local (`client/src/fields.ts`, même introspection des schémas Zod, limites toujours inlinées au build) ; `SafeAreaTopScrim` recréé (`client/src/safe-area.tsx`) ; les styles du conteneur racine sont dans `theme.css` (`.nexora-root`) ; notice d'échec locale (`client/src/failure-notice.ts`). **Ce qui reste de l'ancien SDK, et pourquoi** : la plateforme historique impose deux points de contact à son build — l'instance TanStack Query partagée et la déclaration des contrats privilégiés via ses helpers. Ils sont conservés tels quels, mais cantonnés : le paquet SDK est **vendoré** (`vendor/space-sdk.tgz`, devDependency — l'installation marche donc partout, y compris sur Render) ; le client construit en autonome remplace le module `client/src/query-client.ts` par `standalone/query-client.ts` (instance locale, mêmes réglages) via un plugin du build — **le bundle client autonome ne contient aucun code du SDK (vérifié)** ; et côté serveur autonome, seuls les helpers de déclaration des contrats viennent du paquet vendoré — HTTP, base Postgres, SMTP et toutes les implémentations sont locaux, aucun service externe de l'ancienne plateforme n'est contacté. `space.json` reste le descripteur de la carte dans l'appli (ignoré par le serveur autonome, il n'empêche pas le démarrage). Seule autre trace conservée : le nom de la sonde de stabilisation `__hatchAuditSettle` que l'outil de vérification de l'hébergeur lit encore (aucune dépendance d'exécution).
- **Variables d'environnement (documentées dans `.env.example`, placeholders uniquement)** : `DATABASE_URL`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI`, `NEXORA_API_KEY`, `GMAIL_APP_PASSWORD` (+ `PORT`, fourni par Render). Règle inchangée : l'environnement gagne sur la table `discord_config`.
- **Inchangés et revérifiés par les tests** : OAuth Discord (bouton, échange du code côté serveur, secret jamais exposé, appli « sniko » Client ID 1571508442114560112, scope identify, pseudo + avatar) ; offres par utilisateur (free par défaut) + badges + `adminSetUserPlan` (24 h / 30 j / 150 j / 365 j) ; `getDiscordRoles` (auth `NEXORA_API_KEY`, refus `unauthorized` sinon) ; Patron réservé à isaac.201294dz@gmail.com ; easter egg « voleur 😄 » pour le pseudo sniko ; inscription en 2 étapes avec vrai code à 6 chiffres, cooldown 30 s, mots de passe scrypt, sessions réelles ; support/demandes par e-mail + tableau de bord Patron ; 5 langues, thème noir et blanc ; toutes les autres actions (`adminOverview`, `adminListUsers`, `orderBotPlan`, `activateBotFree`, …).
